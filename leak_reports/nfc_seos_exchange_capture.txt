HID reader NFC exchange capture (reader C0:60:33:15:2B:31)
==========================================================
Captured live with the Flipper `hid_recon` app emulating STANDARD_SEOS as an
ISO14443-4A card, replying 9000 to keep the reader talking. This is the reader's
own credential-hunt sequence over NFC. Reader -> emulated card, full hex:

01< 00A4040010 A0000004400001010001000047052B03 00     SELECT AID STANDARD_SEOS
02< 80A5040066 <OID list>                                SELECT ADF (config leak)
03< 905A000003 000000 00                                 proprietary HID cmd (90 5A)
04< 905A000003 B0BBBB 00                                 proprietary HID cmd (90 5A), retry
05< 00A404000B A00000067660091E052B03 14                 SELECT AID HID-mobile (RID A0000006 76)
06< 00A404000A A000000382002D000101 00                   SELECT AID MOBILE_SEOS_ADMIN_CARD
07< 80A504002A <OID list>                                SELECT ADF (admin ADFs)
08< 00A404000A A000000382002F000101 00                   SELECT AID OPERATION_SELECTOR

  APDU 7: 1.3.6.1.4.1.29240.1.1.2.1.24.1.1.163.11433.1

The "90 5A" command — decoded as MIFARE DESFire SelectApplication:
  CLA=90 INS=5A P1P2=0000 Lc=03 DATA=000000 | B0BBBB   Le=00
  This is the EXACT wire signature of a wrapped MIFARE DESFire native command:
  CLA 0x90 (wrapped), INS = DESFire command (0x5A = SelectApplication), Lc 3,
  a 3-byte AID, Le 00. First AID 000000 = the PICC master application (the
  mandatory first select); second AID B0BBBB = a specific DESFire application.
  So the reader probes for a MIFARE DESFire credential on the 14443-4A card,
  consistent with the MifareDesfireEV1/EV3 KeyType.

  CAVEAT (tested): replying with the DESFire success status 91 00 to both
  SelectApplication calls did NOT make the reader advance to DESFire
  authentication/read — it still sends exactly these two selects and then moves
  on to the mobile AIDs. So either (a) the reader needs a fuller valid DESFire
  card presentation (GetVersion identity, the real app + PACS file, and it only
  commits once those look right), or (b) 90 5A is a fixed 2-step DESFire
  presence probe. Either way, actually serving a DESFire PACS credential would
  require the app's diversified AES key (the same non-exportable-key wall as
  SEOS), which we do not have.

WHY NO AKE CHALLENGE WAS CAPTURED
---------------------------------
The reader never issues its SEOS authenticated key exchange (AKE) challenge,
because it never gets a valid response to the `90 5A` gate (or a valid SEOS ADF
selection response) from our emulator. It selects STANDARD_SEOS, lists ADFs,
sends `90 5A`, gets a junk 9000, and gives up on SEOS -- then tries the HID
mobile credential AID, the mobile admin card, and the operation selector in
turn, failing each the same way. To reach the AKE we would have to answer
`90 5A` and the SEOS ADF selection with valid card-side responses, which
requires the SEOS card-side protocol details (obfuscated) AND, ultimately, the
credential's keys to answer the AKE cryptogram -- neither of which we have. The
attached SAM is a reader-side (terminal) CCID SAM used by seader to *read*
credentials, not a card-side crypto oracle, so it cannot produce these
responses. See MOBILE_KEYS.md and PROTOCOL.md sec 22.
